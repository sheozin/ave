# Check-in Module — QR/Email Delivery — Design Spec

**Status:** Approved by user, ready for implementation planning.

## What this is

The first sub-project of "Plan 1b" (per the check-in module's original build order: QR/email delivery → check-in station UI → print agent → admin dashboard integration → organizer dashboard). This piece delivers each attendee's `qr_token` (already generated by `checkin-import-attendees`, Phase 1a) to them by email, so they have something to present at check-in. It does **not** build the check-in station UI, the print agent, or any admin dashboard screen — those are separate specs.

## Background / why this shape

Real event registration varies by organizer:
- Some organizers already run registration through their own platform (Eventbrite, Cvent, a custom form) and have already emailed attendees a QR/confirmation before ever importing the list into CueDeck. For these organizers, CueDeck's check-in module is purely the on-site verification/badge-printing step — an extra QR email from CueDeck would be a confusing duplicate, sent to their attendees without their intent.
- Other organizers want CueDeck to be the actual delivery channel — no separate registration system, just a CSV import and CueDeck handles getting the QR to each attendee.

The design must support both without forcing either. It does this with a per-event toggle, defaulted to the safer failure mode (see below).

A QR code is a check-in **token**, not a badge. The attendee still gets verified and their physical badge printed on-site — the email must not read as "your ticket" or imply a skip-the-line pass.

## Architecture

One new shared module, `supabase/functions/_shared/qr-email.ts`, holding the actual "generate a QR image + render the email + send via Resend" logic — mirroring how `_shared/resend.ts` and `_shared/transition.ts` already work as shared code imported by multiple Edge Functions, rather than one Edge Function calling another over HTTP for what's really one operation with two triggers:

- **`checkin-import-attendees`** (existing, modified) calls it internally right after a successful (non-dry-run) import, for newly-*created* attendee IDs only — never for updated/re-imported rows — gated by the per-event toggle.
- **`checkin-send-qr-emails`** (new) is the organizer-facing manual trigger: send-to-all-unsent, or an explicit resend to specific attendees. This is what a future "resend" button (in whatever admin UI eventually gets built) will call, and it works today via direct API call regardless of the toggle state.

## Data model changes (two new columns, no new tables)

```sql
ALTER TABLE leod_checkin_attendees
  ADD COLUMN IF NOT EXISTS qr_email_sent_at TIMESTAMPTZ;

ALTER TABLE leod_checkin_entitlements
  ADD COLUMN IF NOT EXISTS auto_send_qr_email BOOLEAN NOT NULL DEFAULT false;
```

- `qr_email_sent_at` (nullable): tracks whether/when an attendee's QR email went out. Used to (a) target "never sent" attendees for the default manual-send call, (b) avoid double-sending on retry, (c) let a future admin UI show send status per attendee.
- `auto_send_qr_email` (default **false**, not true): the per-event toggle. Defaults off because the failure modes aren't symmetric — an organizer who forgot to enable it just flips a switch or calls the manual endpoint (and search-by-name still works as an on-site fallback regardless); an organizer who didn't want CueDeck emailing their attendees and gets a surprise duplicate email the moment they import a CSV is a real trust problem. No existing RLS policy needs to change for either column — they're columns on tables already covered by `checkin_att_read/write` and `checkin_ent_read` (no write policy exists on entitlements at all, unchanged; this column is set via `checkin-enable-event`'s service-role upsert, same as the other four entitlement flags).

## `_shared/qr-email.ts` — shared logic

```typescript
interface QrEmailAttendee {
  id: string
  first_name: string
  email: string | null
  qr_token: string
}
interface QrEmailEvent {
  name: string
  date: string        // ISO date
  venue: string | null
}

// Returns per-attendee outcome so callers can build their own summary.
interface QrEmailResult {
  attendee_id: string
  status: 'sent' | 'skipped_no_email' | 'error'
  error?: string
}

async function sendQrEmailsForAttendees(
  sb: SupabaseClient,       // service-role client, already constructed by the caller
  event: QrEmailEvent,
  attendees: QrEmailAttendee[],
): Promise<QrEmailResult[]>
```

Per attendee:
1. Skip (status `skipped_no_email`) if `email` is null — matches import's existing optional-email stance, no error.
2. Generate a QR SVG from `qr_token` (see "QR generation" below).
3. Render the email (see "Email content" below).
4. Send via the existing `sendEmail()` helper in `_shared/resend.ts`.
5. On success: `UPDATE leod_checkin_attendees SET qr_email_sent_at = now() WHERE id = attendee.id`, status `sent`.
6. On failure: leave `qr_email_sent_at` untouched (stays eligible for retry), status `error` with the message — logged via `console.error` by the caller, not swallowed.

## QR generation

Render as an inline SVG (or PNG data URI) directly in Deno, using a small QR-generating library imported the same way `@supabase/supabase-js` already is (`https://esm.sh/<package>`). No external QR-image API — that would leak `qr_token` to a third party in a URL and add a live runtime dependency every time the email is *viewed*, not just sent.

## `checkin-send-qr-emails` (new Edge Function)

Same auth/CORS/`_ping` scaffolding as `checkin-enable-event` and `checkin-import-attendees`.

- **Auth:** organizer-only, via `leod_checkin_operators.role = 'organizer'` for `event_id` (same pattern as `checkin-import-attendees`), **plus** an explicit `leod_checkin_entitlements.checkin_core = true` check for the event — matching the entitlement-gating precedent just established for `checkin-import-attendees` (migration 051 + its own explicit check). This function uses the service-role client and bypasses RLS entirely, so — same as import — the entitlements check has to be explicit here too; it isn't inherited from anywhere.
- **Input:** `{ event_id: string, attendee_ids?: string[] }`.
  - `attendee_ids` omitted → target every attendee for the event with `qr_email_sent_at IS NULL`.
  - `attendee_ids` provided → explicit resend for exactly those IDs, regardless of prior send state. Resend always reuses the attendee's existing `qr_token` — it is never regenerated. Regenerating would invalidate anything the attendee already saved from a prior email, which is exactly the property `checkin-import-attendees`'s dedup logic (Task 8) was built to protect.
- **Response:** `{ ok: true, summary: { total, sent, skipped_no_email, errored }, send_errors?: QrEmailResult[] }` (only present when non-empty, matching `checkin-import-attendees`'s `update_errors` convention).

## Auto-send integration in `checkin-import-attendees`

After the `toInsert` insert succeeds (non-dry-run path only):
1. Re-use the entitlements row already fetched for the `checkin_core` check (Task 8's post-hardening version) — add `auto_send_qr_email` to that same `SELECT`, no extra round-trip.
2. If `auto_send_qr_email` is true, call `sendQrEmailsForAttendees()` for exactly the rows just inserted (their `id`s are known from the insert — need to switch `toInsert`'s `.insert(toInsert)` call to `.insert(toInsert).select('id, first_name, email, qr_token')` to get them back, since the existing code doesn't currently ask for the inserted rows).
3. Any send failures are `console.error`-logged; they do not fail the import response — the import itself succeeded regardless of email delivery, matching the existing "email delivery is best-effort" precedent from `checkin-enable-event`'s organizer-grant upsert.

## Email content (hybrid branding, per user approval)

- **From name:** `"{event.name} Check-in"`; from address: existing `FROM_EMAIL` env var (unchanged mechanism, no new sending domain).
- **Subject:** `"Your check-in QR code — {event.name}"`.
- **Header:** event name, date, venue — no CueDeck logo.
- **Body:** greeting with attendee first name, one line ("Show this QR code at the entrance to check in") — deliberately phrased as a verification step, not a skip-the-line pass — QR image, one small line ("Lost this email? Just show your name at the entrance instead") tying into the station UI's planned search-by-name fallback.
- **Footer:** small "Check-in powered by CueDeck" credit line — quiet, not prominent.

## Testing

Pure-logic tests (matching this repo's no-live-DB convention, same as `tests/checkin-import.spec.ts`):
- Targeting logic: omitted `attendee_ids` selects only `qr_email_sent_at IS NULL` rows; explicit `attendee_ids` selects exactly those regardless of send state.
- No-email skip: an attendee with `email: null` produces `skipped_no_email`, not an error, and isn't sent to Resend.
- Auto-send gate: fires only when `auto_send_qr_email` is true AND only for newly-inserted attendee IDs, never for updated ones.
- Resend token reuse: the email payload always uses the attendee's existing `qr_token`, never a freshly generated one.
- `checkin-send-qr-emails`'s entitlement gate: rejected when `checkin_core` is false or missing, same as `checkin-import-attendees`.

QR SVG rendering and actual Resend delivery are not unit-tested — no precedent for that anywhere in this codebase (Resend calls are verified via a real send + inbox check, same as prior Edge Functions in this plan).

## Explicitly out of scope

- The check-in station UI, print agent, and any admin dashboard screen (separate specs/plans).
- Attendee-uploaded/organizer logo branding in the email (noted as a future enhancement, not v1).
- A dedicated `checkin@cuedeck.io`-style sending domain (uses the existing `FROM_EMAIL` mechanism).
